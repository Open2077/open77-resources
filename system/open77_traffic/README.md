# open77_traffic

This resource fills the roads around every player with server-owned ambient cars and NPC drivers, driven by the game's own traffic system, and gives operators a panel to tune, pause and reset the fleet.
`open77_traffic` is an optional server resource that runs whole-map ambient traffic on the engine's own traffic enrollment: one `Open77.vehicles.ai.joinTraffic` task per car, executed natively as `AIVehicleJoinTrafficCommand`.

- **Docs:** [Networked vehicle AI](https://open2077.net/docs/vehicle-ai)
- **Starts:** on its own
- **Needs:** nothing
- **Runs on:** server and client

## Enable it

Add `open77_traffic` to `resources.load` in `server.jsonc` **and** opt in to generation with a convar, then restart the server:

```jsonc
"convars": { "open77_traffic_enabled": "true" }
```

Without the convar the resource starts with `enabled = false` and spawns nothing, so a profile that loads every resource with `"*"` does not start traffic by accident. The convar only chooses the default: a value persisted from the panel, Warden or `tunable.set` wins, and because `tunables.json` sits next to the server configuration, such a value (including the `enabled = true` a panel reset writes) applies to every profile in that directory. `server/server.traffic-local.jsonc` is the private two-player profile with traffic on. Its manifest uses `auto_start true`; players do not run a spawn command. On a running development server that already selected it, use:

```text
ensure open77_traffic
```

From the server console, or an identity holding `command.traffic.status`, `traffic.status` prints active and total cars, the global maximum and admitted budget, core AI jobs and per-simulator limit, the span catalog's span and spawn-sample counts, rejected sample/profile counts, and killed drivers awaiting corpse cleanup.

In game, an identity holding `command.traffic.esp` can toggle `/traffic.esp`: on that player's screen only, every streamed replicated car within 150 m (nearest 32, the anchor quota) gets a label 1.8 m above it with its server vehicle id and physics owner (`4294967332 o5`, `o-` when unowned), refreshed every 250 ms and removed when the car leaves range, on the next toggle or when the resource stops.

## The operator panel

`traffic` is the panel's only server surface. It is registered restricted, so a player needs `command.traffic` in the ACL and the console keeps its own path; every request travels the ordinary `open77:command:execute` channel, and nothing in a request names a player: the player a snapshot describes is always the authenticated source of the command. In game, `/traffic` (or the page's own command line) opens the panel.

| Command | What it does |
| --- | --- |
| `traffic`, `traffic open`, `traffic none` | pushes the first snapshot (`open77_traffic:panel:open`), radius default 100 m |
| `traffic state <radius>` | pushes a snapshot (`open77_traffic:panel:data`) at 1..500 m from the caller |
| `traffic set <key> <value>` | writes one setting through `Open77.tunables.set` and answers `open77_traffic:panel:result` |
| `traffic pattern <default\|stop> <radius>` | asks every tracked car of the caller's bucket within that radius for a pattern |
| `traffic panic <radius>` | asks every tracked car of the caller's bucket within that radius for a panic reaction, with the caller as the threat |
| `traffic reset confirm` | deletes this resource's own fleet and restarts generation |

The radius is measured from the authenticated caller's own position, in their own routing bucket, against this resource's tracked cars only. A snapshot carries settings, fleet counts, the server-wide car limit, the current admission budget, core/per-simulator capacity and operational phase counts. Nearby rows show id, record, simulator owner, operational phase/reason, pattern, native pattern status/reason, panic status/reason, measured speed in m/s, and distance in metres; the nearby block also counts panics `active`, `pending` and `notApplied` (blocked or refused). Rows are capped at 12 nearest-first; nearby totals count every match. A pattern or panic result describes the request, not native execution: only a later `patternStatus` / `panicStatus` acknowledges its outcome.

## Settings

All settings are declared in `shared/config.lua` and owned by the host as `Open77.tunables`, which means the panel, the Warden settings form and the console (`tunable.set open77_traffic <key> <value>`) all write the same value through the same validation, and every one of them persists: a change survives a resource reload, a stop and a server restart, and it comes back with its stored value even if a key leaves the declaration and rejoins it. `tunable.reset open77_traffic <key>` is what forgets an override. `traffic reset` is not a settings reset: it clears the fleet, and the one setting it writes is `enabled = true`, because a reset is meant to resume spawning. The panel shows them in the groups Density (`enabled` to `retireDistance`), Spawning (`spawnEveryMs` to `groundFailureLimit`), Timeouts, Reactions and Players, in the order of this table.

| Key | Default | Bounds | Effect |
| --- | --- | --- | --- |
| `enabled` | `false`, `true` with the `open77_traffic_enabled` convar | none | spawn and drive ambient traffic at all; switching it off leaves existing cars running |
| `carsGlobal` | `20000` | 0..20000 | hard limit on this resource's cars across the server; `0` spawns nothing |
| `maxCarsPerArea` | `60` | 1..1000 | no spawn in a player's density area that already holds this many cars; cars driving in are not removed |
| `playerAreaRadius` | `250` m | 50..350 | radius of each player's density area; grows by a fifth and leans ahead at speed, like the native crowd area. Must stay above `minimumPlayerSpawnDistance` |
| `densityScale` | `1` | 0..10 | multiplier on the authored density; `0` spawns nothing |
| `densityFloor` / `densityFloorDriving` | `0` | 0..1 | lowest density coefficient a road gets with the player on foot / in a vehicle |
| `timePeriod` | `0` | 0..3 | which of the four authored density periods to use; the server has no time of day yet |
| `retireDistance` | `250` m | 100..425 | out-of-range retirement after 10 s without a nearby player; effective threshold is at least `groundProbeRadius + 50` m and at most 425 m |
| `spawnEveryMs` | `10` ms | 10..60000 | wait between spawn cycles |
| `groundProbeRadius` | `180` m | 20..500 | outer edge of the spawn band and reach of the candidate sweep |
| `minimumPlayerSpawnDistance` | `60` m | 0..500 | horizontal exclusion around current/recent same-bucket player presence, regardless of height; cached presence is exclusion-only, never a spawn sponsor |
| `minimumSpawnSeparation` | `5` m | 5..200 | centre-to-centre exclusion at the create point and against the fleet; both use at least 20 m |
| `spawnLiftMetres` | `0.35` m | 0..20 | height above the sampled ground the car is created at |
| `launchSpeed` | `10` m/s | 0..25 | speed along its lane a car already has when its first player takes it over (`Open77.vehicles.setLaunchVelocity`), lowered so it can stop 12 m short of the nearest vehicle ahead at 3 m/s²; `0` spawns cars at rest. A client that takes the car over more than 6 s after its create starts it from rest |
| `clearanceAttempts` | `3` | 1..10 | candidates tried per cycle when the final clearance refuses one |
| `groundFailureLimit` | `2` | 1..100 | consecutive close-range ground misses before that candidate is quarantined for 300 s |
| `orphanSeconds` | `10` s | 10..3600 | how long a car may have no simulator after having had one |
| `neverOwnedSeconds` | `10` s | 10..3600 | how long a car may go without ever acquiring a simulator |
| `timeoutMilliseconds` | `3600000` ms | 1000..3600000 | lifetime of each submitted traffic task; a stalled join may be retried up to twelve times |
| `panicResources` | empty | text, 256 characters (panel: 32) | server resources allowed to call the `panic` / `panicState` exports, by exact name, separated by `+` in the panel; empty or `none` allows no other resource |
| `driversKillable` | `true` | none | players may kill drivers; off makes every living driver `immortal` at once, creates new ones `immortal` and refuses player damage (see [Killed drivers](#killed-drivers)) |
| `carsStealable` | `true` | none | players may take these cars; off locks every car this resource created, released and stolen ones included, for everyone and creates new ones locked; on unlocks them all (see [Locked cars](#locked-cars)) |
| `driverDamageScale` | `1` | 0.01..10 | live multiplier on the server's explicit weapon/kind prices; never native damage, perks or headshots |
| `driverHitsPerSecond` | `16` | 1..16 | shared per-player observation budget, one second of burst; melee additionally has a 10/s ceiling |
| `driverDamagePerSecond` | `220` HP | 1..1000 | shared per-player server-priced damage budget, one second of burst; must cover one scaled class price to admit that class |

A change takes effect on the next spawn pass rather than on the next restart: the resource captures the values once (so the admission scan pays no host getter per comparison), re-derives the squared separation gate and the clearance radius from them, and moves its generation counter so a pass that selected under the old numbers cannot create under the new ones. `driversKillable` and `carsStealable` also reach the drivers and cars already in the world at once, in bounded chunks of 64 per scheduler resume, each logged with how many it changed. Two relations cannot be expressed as per-key bounds: `minimumPlayerSpawnDistance <= groundProbeRadius`, because a candidate has to be inside the band around its player, and `playerAreaRadius > minimumPlayerSpawnDistance`, because a sample also has to be inside the player's area (otherwise a standing player gets no spawn). The panel refuses a write that would break either and names the pair; a write from the console or the Warden form cannot be refused after the fact, so it is applied and logged, and every gate stays conservative on its own numbers (the create-point exclusion never drops below 20 m whatever the separation says). The same warning is logged at startup if persisted settings already break a relation; nothing is clamped. `minimumSpawnSeparation` has no relation to the probe radius: it separates two cars, so a separation wider than the band is a legitimate way to admit fewer cars.

The bounds are safety bounds, not taste: a distance below its minimum stops being conservative, `spawnEveryMs` below its minimum spins the loop, and a population budget of zero admits nothing. `groundProbeRadius` bounds the spatial search, whose work is chunked across scheduler resumes rather than assumed to fit one. `timeoutMilliseconds` matches the range the driving service itself accepts.

## Patterns

`Open77.vehicles.ai.setTrafficPattern(vehicleId, pattern)` requests one of the two native traffic patterns (`default`, `stop`) for a car that already has a live traffic task. It never replaces, renews or cancels the join task, so a pattern never costs a car its driving intent; `joinTraffic` takes the same `pattern` option for a task that should start on one, defaulting to `default`. An accepted pattern also ends a panic still pending or running on that car (`panicStatus` `cancelled`, `panicReason` `pattern_changed`), so a Stop or Normal sent during a panic is never undone by it.

The request is one thing and the native outcome is another. A request that the driving service accepts puts the car's `patternStatus` back to `pending`; the client that owns the car applies the pattern through the evidenced `CrowdMemberComponent.ChangeMoveType` path, once per task, epoch, native incarnation and join command, and reports the result back through the existing native bridge as `patternApplied` / `patternFailed`. Only then does a snapshot report `applied` (the engine accepted it on the current executor, not a permanently forced speed) or `failed` with a bounded reason such as `unsupported_pattern`, `component_unavailable` or `native_rejected`. A client that cannot apply the pattern retries the component and the native call inside its bounded window and then reports the failure without cancelling the driving task, so a refused pattern leaves the car driving normally. A handoff to a new simulator puts the status back to `pending` for the new executor, and a car whose task is gone reports `inactive`.

The panel's `traffic pattern <name> <radius>` therefore reports a request: how many cars matched its bucket and radius, how many took the request and how many refused it on the spot (for example `traffic_pattern_inactive` when the car has no live traffic task). It never reports a native success the server cannot know yet.

## Panic

Panic is not a pattern. The engine's crowd `panic` move type, held on a join, left junction-dense traffic standing still while reporting the move type accepted, so it is not offered. A panic is instead the driving service's own time-bounded reaction, `Open77.vehicles.ai.panic(vehicleId, options)`: the simulating client releases the car's kinematic join, waits until the engine really holds no slot and no command, sends the engine's own `AIVehiclePanicCommand`, and reports `active` only once it observes that command executing. The duration starts there, not at the request; the car then returns to its join through the bounded collision-recovery path. Details are in the [Networked vehicle AI](https://open2077.net/docs/vehicle-ai) guide.

This resource owns its cars' driving tasks, and the driving service refuses every command for them from any other resource. The one supported path for another resource is this resource's export, which the panel's own **PANIC** button goes through as well:

```lua
-- After an explosion at `blast` in the caller's bucket, for a car it selected:
local view, reason = exports.open77_traffic:panic(vehicleId, {
    threatPosition = { x = blast.x, y = blast.y, z = blast.z },
    threatKind = "player", threatId = shooterId,   -- optional
    durationMilliseconds = 8000,                   -- 1000..30000, default 10000
})
-- view = { vehicleId, request, status = "pending", reason, durationMs, remainingMs }
-- later: exports.open77_traffic:panicState(vehicleId).request == view.request
--        and .status is active / ended / blocked / refused / cancelled
```

Only resources the operator lists in the `panicResources` setting may call `panic` and `panicState`; anyone else gets `forbidden_resource`, and a car this resource does not track gets `not_traffic_vehicle`. Every accepted call is a new request with a new `request` token that replaces the previous one: repeated shots keep a car panicking for the duration after the last one, and an older request's timer never ends a newer one. A status that no longer names your token was replaced. Outcomes: `active` (native command executing), `ended` (`duration_elapsed`, or the engine finished it on its own), `blocked` (`join_unreleased`, `not_executing`, `application_timeout`: nobody confirmed it within 5 s), `refused` (`native_rejected`, `unsupported_vehicle`, ...), `cancelled` (`replaced`, `pattern_changed`, or the task's own end reason such as `driver_unavailable`). The panel's `traffic panic <radius>` makes the same request for every car in range, with the operator as the threat, and reports how many took it; the Status column then shows `pending`, `active`, and why a car did not panic.

## Reset

`traffic reset confirm` deletes every vehicle and driver NPC this resource created and then resumes generation. It is deliberately two-step (a bare `traffic reset` refuses) and it is destructive for the cars it removes.

- **Scope: everything this resource owns.** The canonical registry is enumerated and every vehicle whose creating `resource` is `open77_traffic` is deleted, whether or not the ledger still tracks it, so a wreck it released to the registry's unobserved sweep and a car it handed over to a player are removed too, and so is a driver ped whose car vanished before the monitor could take it out (the ped registry is owner-scoped, so the sweep can only ever see this resource's own peds). A car another resource made is named and left alone: the `resource` field is re-checked per row, and a ledger entry the registry now attributes elsewhere is dropped rather than acted on. Occupied traffic cars ARE in scope: each occupant is put on their feet through the canonical seat API before the body goes, and the registry publishes the seat's own fate when the vehicle is removed, so nobody is left seated in a car that no longer exists.
- **Settings are kept, generation is switched on.** Reset clears traffic: the fleet, the spawn-sample reservations, the run's quarantine sets, the ground-failure counts and the population bag's position. The one setting it writes is `enabled = true`, through the same validated, persisted path the panel uses, so a reset resumes spawning even if traffic had been switched off before it, and because the host owns that value, a write it refuses refuses the reset: the fleet and the configuration are left exactly as they were.
- **One reset at a time.** The deletion yields between bounded chunks, so a second reset can be scheduled into the middle of the first. It is refused before it fences the generation, before it switches generation on and before it reads the registry: two interleaved resets would clear each other's flag and each clear a fleet the other was still walking, and a car created in the gap would outlive a reset that claimed to have removed everything.
- **Stale work cannot survive it.** The reset moves the generation counter before it deletes anything, and the spawn thread and the retirement monitor stand down for its whole duration. A pass parked at a scan `Wait(0)` or at a client ground query resumes to find its generation gone and refuses to create: the reset cannot resurrect work that was already in flight, and it cannot be walked past by it. The bookkeeping is settled per car rather than by wiping the tables, so nothing that somehow reached the ledger across a yield is orphaned, and if that ever happened it is logged instead of being swallowed.
- **Failures are reported.** The result names what was removed and counts anything that could not be, rather than claiming a clean reset.

## Runtime model

The resource only owns population policy and spawn placement. The driving intent is one submission per car:

1. Read authoritative positions only for players whose readiness gate is open and whose life phase is `alive`.
2. Fill each such player's density area the way the game's crowd system does. The area is a circle of `playerAreaRadius` (250 m by default) that grows by a fifth and leans ahead with the player's server velocity; one holding `maxCarsPerArea` cars, or already its total desired density, spawns nothing. A span of the catalog (one authored crowd fragment of a road lane) wants `max(coeff, floor) · desired[timePeriod] · densityScale` cars, `coeff` being the fragment's mounted value while the player sits in any vehicle, prorated by the share of its spawn samples inside the area; its deficit is that minus this resource's cars counted on it inside the area (a car counts on the span of its nearest sample within 9 m and 3 m height whose direction is within 45° of the car's yaw). Per bucket each span keeps its largest deficit over open areas, and spans are tried by deficit per metre of span inside the area, each held for 5 s after a spawn or a failed placement, as natively. The chosen span's samples are tried from a random start: a sample must lie between `minimumPlayerSpawnDistance` and `groundProbeRadius` (60 m and 180 m by default) from that player, not in the half-plane behind a player above 10 m/s, and pass the reservation, quarantine and 20 m separation gates; the first allowed sample ends the pass. Each selection pass snapshots the fleet's current canonical poses once (falling back to the retirement monitor's copy only when a record is unavailable), rather than reading every car again for every candidate. Fleet reads, candidate visits and inner comparisons share a 4,096-unit work allowance per resume (12 per fleet read, 4 per candidate, 2 per comparison). `Wait(0)` continues an unfinished scan next tick without raising the Lua instruction quota; generation fences revalidate after a yield.
3. Revalidate the selected player and fleet admission, then run the vehicle clearance query (step 4) and all-player exclusion at the catalog sample: both are server-local and do not yield, so a point already occupied is refused without paying a client raycast. Only then query that client for ground height. After the reply, recheck readiness, life, routing bucket, the selecting player's horizontal minimum distance and 3D maximum distance, and current fleet admission. A player who left makes the reply obsolete: release the reservation without spawning or charging a ground-failure strike. The core simulator election admits a new owner within 350 m and retains it to 425 m. Per-attempt deferrals (pre-check, final clearance, fleet moved, ground miss) are counted and logged as one `spawn deferrals in the last 10 s` summary line instead of one line each; the rare fence refusals (obsolete ground reply, pass invalidated before the create) keep their own line naming the cause.
4. Run the final clearance guard at the exact create point (the sampled ground plus the 0.35 m chassis lift, not the catalog sample) with no yield before creation. The canonical same-bucket proximity query must find no registered vehicle within 20 m (or a larger configured `minimumSpawnSeparation`). Current/recent same-bucket player presence must also leave the horizontal `minimumPlayerSpawnDistance` clear, including players directly above or below the point and the path a moving player covers in the next 1.5 s (plus the age of their pose). Cached presence only blocks creation; the selected sponsor must still have fresh ready/alive authority data. The outer `groundProbeRadius` applies only to that sponsor. Unavailable or malformed query results defer rather than guess. A blocked candidate is dropped for that pass only and the next-best candidate is tried; the reservation is released without quarantine.
5. Draw one qualified vehicle/driver profile from a server-seeded weighted shuffle bag, then one vehicle appearance and one driver appearance from that profile's authored pools. The clearance guard runs before this draw, so a refused candidate does not consume a bag position.
6. Create one canonical server vehicle 0.35 m above the sampled ground (already locked while `carsStealable` is off) and one frozen canonical NPC driver with native pedestrian behavior disabled, `mortal` while `driversKillable` is on and `immortal` otherwise, each wearing the drawn appearance, then attach the driver. `mortal` is set here, not by default: `Open77.npcs.create` keeps its protective `immortal` default for every other resource.
7. Submit one `Open77.vehicles.ai.joinTraffic` task for the created car with the bounded task lifetime. The task carries no waypoints, no speed and no behavior: the join command reads none of them. A client does not advertise simulator readiness or issue the native driving command until its NPC projection is confirmed in that vehicle's front-left seat.
8. Hold that command. The engine crosses its own lane and path boundaries without a new task, so the resource never replaces or renews a working car's driving intent; only a stalled car's join is retried, up to twelve times. A live, unoccupied, non-stalled car with a living driver retires after `orphanSeconds` without its former simulator or `neverOwnedSeconds` without ever acquiring one, even while a player is in range. Separately, 10 s of continuous absence of every bucket player from the removal distance (`retireDistance`, default 250 m, never below the maximum spawn distance + 50 m nor above the 425 m streaming edge; the per-area limit only counts nearby cars, so a 425 m window let far cars fill a player's simulator) retires out-of-range cars. A car outside every player's density area, with every same-bucket player within 425 m moving away from it above 10 m/s, is retired after 2 s even while streamed (`retired reason=trailing`). Temporary stops at lights or in traffic do not retire or retry a car.

It does not elect a simulator, accept vehicle transforms, or issue driving commands itself. `VehicleDrivingService` elects one ready viewer, `VehicleAuthorityService` grants that client a short epoch-bound physics lease, and every other client renders the canonical server motion.

Admission is separate from the population limits. `Open77.vehicles.ai.capacity()` returns `globalUsed` (every resource's attached AI jobs; the server imposes no total), `perSimulatorLimit`, and `owners` (decimal player-ID keys, booked slot counts). `attachDriver(vehicleId, {npcId=driverId, admissionPlayerId=playerId})` reserves a simulator slot while the projections are enrolling; a full reservation returns `ai_simulator_limit`. The reservation does not force ownership and transfers with the grant. Nearest-owner election is on by default: unowned cars prefer any eligible viewer below `perSimulatorLimit` (default 32), using up to 16 extra slots only when none is below it (still capped at 128). Within each band, healthy simulators come first, then distance score with a speed-scaled driving bonus and player ID. Owned moving cars may transfer to a healthy receiver below the limit through the nearest path (15 m score margin, 1.5 s hold, rate limited, incumbent bonus never below its acquisition bonus). The contact path may transfer moving or stopped cars to a healthy eligible driver above 5 m/s within 30 m, up to the extra budget, after both the 1.5 s ownership hold and the 1.5 s post-contact hold; a contact-driver owner needs a 10 m closer challenger, and the nearest path retains it within 30 m. `OP77_AI_NEAREST_OWNER=0` restores health-first, least-loaded-then-nearest election without extra slots or proximity/contact reassignments; eligible owners keep their cars.

The generator excludes full sponsors before searching roads, rechecks after yielding, and reserves at attachment. It also reads `Open77.npcs.capacity()` (`resourceUsed`, `resourceLimit`, `globalUsed`, `globalLimit`) before selection, after yielding selection, and immediately before creation. No free driver slot means no ground query or partial vehicle creation. The admitted population budget is capped by both available simulator slots and remaining resource/global NPC slots; residual create-time races still use the existing capacity refusal cleanup. `simulation.maximumAiVehiclesPerSimulator` configures admission (1..128, the server's per-simulator ceiling); there is no total AI job limit. A configured limit is not a performance certification.

Operational phases distinguish `enrolling`, `moving`, `healthy_waiting`, `recovering`, and `failed_retiring`. The native executor reports execution/recovery with the current task, revision, authority epoch and native binding; only the current simulator's report is accepted. Healthy waiting requires both native execution and a fresh accepted physics sample, so a ready projection or stationary unexecuted task is not reported as healthy traffic.

Observation and authority freshness are separate. A last fresh player position may block spawn clearance and preserve a visible fleet/corpse for up to 30 s; missing movement, death or temporary unreadiness do not renew that cache. Disconnect and bucket-change events discard it immediately. Cached positions never sponsor spawns, elect/retain simulators, admit transforms or authorize damage. Once no current/recent same-bucket presence sees a car, ten continuous seconds of absence are required for ordinary out-of-range retirement; simulator loss and non-acquisition instead use their own timeouts regardless of observation. Fleet and corpse maintenance yield after eight entries, re-read canonical state in each chunk, and stop if reset/settings generation changed.

Six consecutive silent or rejected simulator grants without an accepted physics capture terminate the existing task as `failed` / `simulator_recovery_failed`; an accepted capture resets that counter. It is not an endless ownerless re-election loop. The traffic resource releases the driver, simulator/density booking and origin reservation at once, even for a previously stalled car in view, while retaining the chassis with non-persistent unobserved cleanup. This does not certify native movement or make cached presence an eligible simulator.


There is deliberately no runtime lane-graph walk, no continuation handoff and no retry state machine beyond re-submitting a stalled car's join. The resource reads each spawn sample's position and heading only: those are the spawn place, the ground-probe target and the initial yaw, not a route the Lua layer drives.

A record-stage spawn failure quarantines that profile. Task lifetime expiry, missing/cancelled tasks, destruction, driver or native lifecycle failures and authority loss do not establish bad road geometry: retirement releases the sample for ordinary replenishment. The one exception is a join that keeps failing at once: two cars in a row from the same sample whose task ends `native_command_failed` within 10 s of their create bench that sample for 300 s like ground failures (otherwise a point that always fails would be picked again every few seconds); any other end of a car from it clears the count. Likewise, two cars from the same lane that stall with `impact_recovery_failed` within 120 s of their create, inside a 180 s window, bench every sample of that lane for 300 s (stalled cars from one lane tend to pile up at the same merge). Ground-query failures retain their bounded quarantine below. Capacity refusals (`vehicle_limit`, `npc_limit`, `npc_resource_limit`, `ai_simulator_limit`) clean up the partial spawn and wait one second without quarantine. Other post-create lifecycle refusals use the same bounded wait. Contact damage and zero movement are not retirement evidence: red lights and lane queues are valid stationary traffic. Retirement follows a terminal task, an orphaned simulator, failure to acquire a simulator, a car beyond every player's removal distance (`retireDistance`, default 250 m), a trailing car (step 8), or the task deadline.

A ground-height query can miss when the selected player has not streamed the sample yet. The controller only probes within `groundProbeRadius` (180 m by default; a larger radius benches many more candidates for missing ground), permits `groundFailureLimit - 1` retries, and quarantines that sample for 300 s once the consecutive misses reach the limit; after that it is eligible again with a fresh count, because the probing client may simply have been streaming the area. A miss more than 150 m from the probing player only holds its span for the 5 s span hold and is not counted. A successful ground probe resets the failure count, and a reset clears every quarantine.

Reservations, per-pass refusals, ground-failure counts and their expiry are scoped to `(bucket, sample)`. The same spawn sample can therefore host one car independently in each bucket; releasing or quarantining it in one instance does not change another. Only record/profile qualification is shared across instances. Reset clears each bucket's failure history while preserving the identity of any reservation whose car could not be removed.

The ground ray starts 1.5 m above the authored road level. Non-finite results or surfaces more than 1.5 m from that level are refused as `road_level_mismatch`, using the same bounded ground quarantine rather than spawning on a different deck. A valid nearby collision height, not the catalogue height, supplies the final chassis elevation. Native recreation uses the current authority's latest pose, never the original create point; motion-stream samples older than two seconds wait for fresh state.

Collision recovery is authority- and native-incarnation-bound. Each locally owned eligible join can release, including AI–AI contacts and contacts with a registered ownerless counterpart; an observer never takes over the physics response. Deferred impulses wait for the native command and traffic slot to release. Recovery preserves one second of free physics, then requires speed at or below 0.5 m/s, upright chassis/front/rear support on the current level, a compatible heading and clear forward probes for one continuous second before reenrollment. There is no lane test: `IsPathIntersectingWithTraffic` across the chassis never passed live, even for cars stopped level and aligned on their road. An unavailable safe rejoin fails at the first native poll after the ten-second deadline. The failed task is latched until the server acknowledges it and cannot immediately restart itself. Neither stale deferred pushes nor full push queues fall back to an impulse against the held lane.

If a player occupies a car when it would otherwise retire, the resource stops the AI, detaches and removes the NPC driver, and releases the car with `persistent = false`, `despawnWhenUnobserved = true`. The canonical registry protects every occupant, including passengers, across ordinary resource stop/restart. After the last occupant exits and the last viewer leaves, the registry removes the car after its thirty-second unobserved grace; no Lua retirement ledger or permanent persistence survives. Explicit `traffic reset confirm` remains a deliberate purge.

A wreck (the canonical record reports `destroyed`/`exploded` or health zero) uses the same unobserved retention, even without occupants: release its spawn sample and preserve the visible chassis. Disposition follows the record, not the task's retirement reason. The driving service keeps a wreck's seated driver attached, and the wreck waits 2 s for canonical driver death before deciding it: a killed driver stays seated (see [Killed drivers](#killed-drivers)), a living one is removed. An unoccupied `failed` / `impact_recovery_failed` car is stalled: while a player of its bucket is within 425 m it stays where it stopped with its driver, and its `joinTraffic` is re-submitted every 5 s after failed attempts, up to twelve retries. A successful execution resumes traffic; after twelve failed retries the car retires even in view, freeing the spot and driver. A stalled `simulator_recovery_failed` car retires immediately with the failed-recovery disposition instead of retrying. A stalled car outside every player's view retires after 10 s without retrying.

### Killed drivers

`driversKillable` (on by default) decides whether drivers can die at all; everything below describes it on. Switched off, every living driver of the fleet is made `immortal` at once, new drivers are created `immortal`, and `open77_traffic:driverDamage` applies nothing, not even a wound. `immortal` is `Open77.npcs.create`'s own default and what traffic drivers were before they became killable: the server floors the body's health at 1, every client keeps its keyed Immortal barrier on the projected body so it cannot die locally, and no client claims or prices a hit on it (only a `mortal` driver's damage is claimed), so a shot plays its hit reaction and nothing else. A driver already killed stays dead and keeps its seat. Switched back on, every living driver is `mortal` again and keeps the health it had.

Ambient drivers use **server-priced damage**, following deathmatch's explicit-price approach without depending on that gamemode at runtime. Native hit contacts are observations, not prices. On every client the managed mortal driver's native health drains and `DriverKill` min-health write are withheld; the claimed native Kill flag is also removed so it cannot independently trigger the ordinary lethal pipeline. A synthetic DriverKill (which bypasses `OnHit`) contributes an ordinary weapon contact, using its source/held weapon when the synthetic event omits one. It has no lethal override. Normal seated death follows canonical zero, not a locally killed body later repaired by resurrection. Only the local player's contacts enter this path; NPC/environment attacks do not wound traffic drivers through it. A car explosion's separate passenger-kill status effect remains outside this native hold.

The public four-argument `open77:npcDamage(npcId, healthFraction, weaponTdbId, attackKind)` remains an independent best-effort native-price observation for other resources. Traffic does **not** forward it or generic `open77:npcHit`. The plugin targets the exact current traffic Lua VM with private `open77_traffic:driverDamageClaim(npcId, count, weapon, kind, incarnation, ageSeconds, sessionGeneration)`. Consecutive same-body/weapon/kind callbacks within 45 ms (100 ms for melee) form one contact observation; later windows increment the count even while delivery is blocked. This is a pellet/contact grouping policy, **not proof of physical trigger pulls**. Health-drain callbacks never add private counts. Native and Lua queues each hold at most 128 observations, rejecting new overflow rather than evicting admitted older observations. Native delivery attempts at most 16 rows per 100 ms; Lua sends at most one packet per 100 ms, with at most 16 rows and 16 total observations, paced by a player-wide 16/s token bucket. Failed handler/network enqueue retains the pending counts. Public receipts are not repeated by private retries. Old world/body/VM/session observations are fenced; observations expire after 30 s. Overflow, expiry, reset and backpressure are counted: this is bounded loss-aware scheduling, not conservation through arbitrary outages or lifecycle resets.

The server accepts bounded integer counts, known kinds, a strictly increasing per-player packet identity and reported ages from 0 to 30 s. It checks the authenticated ready/living shooter, this resource's tracked living mortal driver, fresh shooter position, matching bucket, and the car's actual server visibility set. Reach is capped by the body's streaming window and PvP per-kind reach plus 6 m: melee 14 m, explosion 56 m, ranged 506 m before the streaming cap. `Open77.data.weapon(hexTweakDbId)` resolves nonzero IDs in the shipped server catalogue; unknown records and unsupported class/kind combinations fail closed. Fresh client-reported equipment may contradict a ranged/melee weapon claim; stowed matching weapons remain valid, a newer loadout cannot disprove an older contact, and explosions need not match the current weapon. Weaponless melee/blasts are explicit policies; weaponless ranged contacts are refused. Packet ingress remains capped at 20/s with a 20-packet burst, in addition to the generic resource-event ingress limits. Counts spend the full shared hit budget (default 16/s; melee additionally 10/s) and price-weighted damage budget (default 220 HP/s), each with one second of burst. Affordable whole observations are applied; every refused remainder is counted rather than silently truncated. Changing targets, folding rows or batching never resets these budgets. Replay watermarks survive rate-window pruning until disconnect. False `applyDamage` results, exceptions and admission refusals share the existing 10 s aggregate summary.

The server's base HP prices are handgun **26**, SMG **18**, rifle **22**, shotgun **58**, double shotgun **62**, sniper **90**, precision rifle **65**, revolver **45**, and light/heavy machine gun **16**. Melee prices are fists/generic melee **25**, knife/axe **35**, one-handed club/Gorilla Arms **45**, katana/long blade/machete/sword/chainsword/Mantis Blades/monowire **55**, and hammer/two-handed club **65**; a firearm bash costs **25**. Knife/axe thrown contacts retain their 35 HP class price. Grenade/launcher contacts and explosions (including explosive firearm rounds and weaponless blasts) cost **70**. `driverDamageScale` multiplies these explicit prices; admitted damage is `min(canonicalHealth, scaledClassPrice * admittedCount)`. A positive float32 remainder no greater than `min(0.001 HP, maxHealth * 0.00001)` is cleared only after computing that affordable server price, so fractional scale arithmetic cannot leave an effectively dead driver alive; a genuine 0.01 HP survivor is preserved. Native fraction, armour mitigation, upgrades, perks, critical/headshot damage and native instant-kill magnitude do **not** alter the canonical price; this traffic model has no headshot bonus or client-fraction lethal correction.

**Trust boundary:** the server owns classification, prices, health/death and weighted admission, but contact occurrence, claimed kind/weapon and age remain client evidence. There is no independent handheld shot/ammunition/line-of-sight ledger, and cached equipment is corroboration, not ownership or hit proof. A compromised nearby visible client can still forge plausible contacts within the server policy; it cannot choose an arbitrary fraction/amount or force a native lethal override. Handler/network enqueue acceptance is not server application acknowledgement. Mounted vehicle weapons retain their separate server damage path, and other resources may damage only NPCs they own.

The driving service ends a killed driver's task as `failed`/`driver_dead` on its next tick and cancels any live panic with the same reason, but keeps the job attached: the body stays in the driver seat, its canonical position follows the car, the seat stays reserved, and every viewer of the car keeps the body streamed. (A driver that vanished or left the bucket is `driver_unavailable` and detached.) The car itself becomes an ordinary parked car: the death revokes its AI simulator once, no simulator is elected for it again and it holds no simulator slot, so it can be pushed and claimed like any unowned car. Each client releases the native command as soon as it learns of the death and plays the vanilla seated death on the mounted body, slumped at the wheel; a client that streams the car in later seats the body first, then poses it. Open77 never unmounts the body, re-seats it after that pose or moves it out of the car, and a player boarding a passenger seat does not drop it out (vanilla would, on that player's client only).

The seat is taken only by stealing it. A plain entry into the driver seat is refused, and so is the passenger's slide across. The vanilla steal at the driver's door asks the server for the seat as an ordinary entry; only once every seat check has passed (same bucket, within 15 m, not locked for that player, not a wreck, no other player in the seat) does the server detach the job as `detached`/`driver_stolen`, before it publishes the occupancy naming the thief. A refused request leaves the body seated and the job attached. The thief's client plays the vanilla `deadstealing` entry, V dragging the body out; every other client plays the body's own vanilla exit and sees the thief get in normally.

The resource decides from the NPC record, not from the task, so the order of the death, the task's end and its own monitor tick does not matter, and it never stops or detaches that task itself (which would unseat the body and overwrite `driver_dead`). The same healthy canonical car is kept -- never deleted, replaced or given another driver -- and leaves the ambient ledger: its spawn sample is released and neither the road nor the profile is held against the death. The car gets the occupied-car disposition, `persistent = false` and `despawnWhenUnobserved = true`, so its killer or any other player can steal it and drive it, a passenger already aboard stays aboard, and once nobody occupies or streams it for thirty seconds the registry removes it. A killed driver's car is no longer traffic: `panic`/`panicState` answer `not_traffic_vehicle` and panel sweeps do not reach it.

The resource never moves the body. While the job still names it, the body stays in its seat for as long as its car exists, however long that is, and is removed with the car. Once it has been dragged out, it is removed 10 s after no player of its bucket is inside its streaming window, at once when its car is removed, and 60 s after the drag-out at the latest. A wreck whose driver was killed -- before, by, or up to 2 s after the explosion -- keeps the body in its seat the same way: the driving service keeps a destroyed car's job attached while its driver is seated, so the body burns with the wreck and goes when the registry removes it. `traffic.status` counts the bodies awaiting cleanup; `traffic reset confirm` removes them with the rest of the fleet.

### Locked cars

`carsStealable` (on by default) decides whether players may take these cars at all. Switched off, it locks every car this resource created, for good: the tracked fleet and every car it has let go of (wrecks, handed-over and stolen cars, killed drivers' cars), found through the canonical registry by creating resource, with `Open77.vehicles.setLockedForAll`, the registry's own server-only lock bit, which also revokes any per-player exception another resource granted. A car spawned while it is off is created locked. Switched back on, every one of them is unlocked for everyone.

The server refuses every seat request on a locked car, driver and passenger alike, before a killed driver's job could be detached, so a killed driver stays at the wheel of a locked car; a player already aboard stays aboard and may get out, but not back in. Only a resource that seats a player itself (`Open77.vehicles.warpPlayerIntoVehicle`) bypasses the lock, by design. Every client projects the bit as vanilla's Locked doors and shows each seat door as vanilla shows a door nobody may open, its inactive quest-locked prompt, and nothing on the trunk or the hood. None of the vehicle record's door actions is offered: no mount, no dead-driver steal, no skill-checked force open (`VehicleCrackLock`), no take-over (`VehicleHijack`); and the local mount gate refuses a seat on a locked car even from a stale prompt. Vanilla's vehicle quickhacks (take control, force brakes, accelerate, detonate) open no door and are not affected.

## Current limits

Resource settings persist across restarts; server admission is configured separately.

- Population limits: 20,000 across the server (`carsGlobal`) and, around each player, the authored density of their area up to 60 cars in it (`maxCarsPerArea` within `playerAreaRadius`, checked at spawn; inbound cars are not removed). The admitted budget is the smaller of `carsGlobal` and the current fleet plus the lesser of ready simulators' free slots and remaining resource/global NPC capacity. Other resources' AI jobs and unowned enrollment reservations consume slots. The canonical vehicle registry (4,096 vehicles) still bounds creation.
- One client's native job table holds up to 4096 AI jobs (the server registry bound), so every AI car it streams gets a local record; a refusal would log `Vehicle AI job table full` once per session.
- Spawn geometry/cadence: one car per spawn sample per bucket at a time (a sample is freed once its car is 30 m from it, so it takes the next car while the first still drives), at least 20 m between live cars, `minimumPlayerSpawnDistance` (60 m by default) from players, a 5 s hold on a span after each spawn or failed placement, and a `spawnEveryMs` wait (10 ms by default) between completed spawn cycles. A dense selection can span multiple server ticks; the cadence is not a promise of a creation every wait.
- Saturation is visible in `traffic.status` and the panel. NPC/simulator capacity is checked before costly spawn work and after yields. Residual create/attach capacity races release partial entities and reservations, then wait one second without condemning a road or profile.
- Client transport load is separate from population admission: a simulator publishes for every car it owns. Older clients retaining GNS's fixed 256 KiB/s send ceiling can disconnect around dense-city loads with `vehicle_owner_state_send_failed:25`. The updated client permits up to 4 MiB/s through congestion control, without increasing its 512 KiB send queue or changing publication cadence. Deploy the client correction as well as this resource; raising Lua car budgets does not repair that transport limit.
- Native-driving dispatch is bounded and round-robin. Older clients that restart every scan at the lowest vehicle ID can leave later cars without any driving command under dense load, despite valid ownership and seated drivers. Deploy the fair-dispatch client correction; increasing spawn or population budgets cannot fix this starvation.
- Final spawn clearance: the create point is cleared against the canonical registry immediately before the create, after the ground probe, in the selecting player's routing bucket. 20 m (or a larger configured `minimumSpawnSeparation`) between centres is a conservative exclusion, not a body-shape test: the registry carries no vehicle bounds, so no per-record footprint is guessed. It sees canonical registered vehicles only: this resource's cars, freeroam/player deliveries, adopted cars and other resources' AI vehicles. Engine-local REDengine population that never entered the registry is invisible to a server-only resource. Positions are the latest server pose, not a client's future physics, and a vehicle on another deck within the radius conservatively refuses the point. A query that is refused, `nil` or malformed defers the attempt rather than spawning on a guess, and a refusal never quarantines the sample or the profile. At most `clearanceAttempts` (3) candidates are probed per attempt, so a refused candidate is dropped only for that pass and the next-best is tried.
- Ambient lifetime: one task per car with `timeoutMilliseconds` (3600000 by default, the maximum the driving service accepts). Nothing renews it; a car that outlives it is retired and replenished by the normal spawn path.
- Retired bodies: wrecks, occupied cars, killed-driver cars and terminal recovery failures use non-persistent unobserved cleanup. A living driver is removed at release; a killed driver remains seated while its car exists and is retained for at most 60 s once dragged out. Occupants survive ordinary resource shutdown; after the last occupant and viewer leave, the registry's thirty-second grace removes the car. Explicit reset/removal can still purge it. Other failed unoccupied live cars use ordinary removal.
- Population profiles: Archer Hella with `LowlifeMaleDriver`, Makigai Maimai with `NightlifeFemaleDriver`, and Thorton Galena with `CitizenRichFemaleDriver`. Each profile also carries the record's verified appearance pools: 9 vehicle variants for the Hella, 7 each for the Maimai and Galena, and the full 14/30/30 driver appearance lists of the three crowd templates. A profile with a missing, empty, non-name or `random` entry fails the catalog load instead of starting.
- Selection is server-only and reproducible from the logged seed. A weighted shuffled bag avoids profile streak starvation. The vehicle and driver appearance are drawn once, at create, from the same seed and travel in the canonical create, so every viewer and every stream-in replays the same variant; nothing re-draws them per tick or per viewer. The engine's stock variant already carries the colour, so no `primaryColor`/`secondaryColor` override is authored.
- Spawn samples: 33,716 samples every 15 m on 5,641 road-lane spans, in a 100 m grid. Samples are not individually live-qualified. Ground failures use a bounded quarantine in the probing bucket; ordinary task retirement and contact damage do not reject the origin road.
- Damage policy: drivers are `mortal` while `driversKillable` is on and `immortal` while it is off; see [Killed drivers](#killed-drivers). Ordinary damage preserves normal lifecycle handling and road eligibility. Wreck release, occupied handover, a killed driver and live-task retirement do not constitute static road-quality evidence. Record-stage profile quarantine is shared; runtime ground history is bucket-local.
- `server/spans-generated.lua` is generated from the game's lane catalogue: one span per crowd fragment on a Road lane (no Pavement, TrafficDisabled, GPSOnly, Blockade, NoAIDriving or NoAutodrive flag, raw speed ≥ 8, width ≥ 4 m) with its four period entries, and spawn samples every 15 m on a 100 m grid.
- The span catalog and the population profiles live in server-only Lua catalogs loaded before `server.lua`; neither is distributed to players.
- A car can acquire a simulator only while a ready, alive player is within 350 m. Its existing owner is retained to 425 m to avoid boundary churn.
- Lane choice, signals and queueing are the engine's; the join command is REDengine's own traffic enrollment, so the server task deliberately has no speed or behavior input. `setSpeed`, `setBehavior` and the `speed`/`behavior` request options are refused with `traffic_speed_unsupported` / `traffic_behavior_unsupported` for a `traffic` task and remain available to the autonomous destination modes.
- `arrived` is not reachable for a join task and remains an invariant breach that retires the car.
- NPC drivers are created frozen with native pedestrian behavior disabled. The client retries the native mount once per second and withholds both simulator readiness and the driving command until `GetMountedVehicle` confirms the expected vehicle and front-left seat. There is no fixed projection warm-up.
