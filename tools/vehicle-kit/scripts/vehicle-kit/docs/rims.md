# Light RP rim catalogue (`lightrp_vk_rims`)

Eighteen original rim designs for the Light RP dealer models, each in six finishes (108
models), built with the vehicle-kit pipeline (`README.md`, one level up). They replace the
stock **rim only**: the stock tyre stays, and each rim is scaled to sit inside that wheel's
own tyre, front and back separately.

| File | Role |
|---|---|
| `blender/make_rim.py` | the generator; the catalogue styles are `classic`, `lattice`, `dish`, `fork`, `blade`, `beadlock`, `aero`, `tech` (swept members) and `star`, `twin`, `yspoke`, `vortex`, `threepiece`, `wire`, `turbofan`, `steelie`, `offroad`, `hex` (window-disc faces) |
| `specs/lightrp-rims.json` | the pack spec: resource `lightrp_vk_rims`, archive `LightRPVehicleKitRims`, palette, parts, finishes, exclusions |
| `specs/lightrp-rims-fit.json` | the mount table: per-record `fit` for contract §5, plus every measured number behind it |
| `specs/lightrp-rims-fit-player.json` | the same for every other vanilla player vehicle (see "Every other player vehicle"); never repeats a record of the table above |
| `player-rim-fit.cjs` | writes `lightrp-rims-fit-player.json` from the player inventory, a `measure-wheels.ps1` run over every wheel variant, and the table above |
| `measure-wheels.ps1` + `measure-wheels.cjs` | measures the stock wheels and writes the fit file |
| `rim-board.ps1` | labelled contact sheets from the pack's renders: all designs in all finishes, a face-on overview, one sheet per design |

```powershell
# Pack (Blender + cp77tools, Cycles CPU previews), into artifacts/vehicle-kit/lightrp_vk_rims
pwsh -NoProfile -ExecutionPolicy Bypass -File scripts/vehicle-kit/build-pack.ps1 -Spec scripts/vehicle-kit/specs/lightrp-rims.json -PreviewViews 4
# Mount table (reads the game archives into %TEMP%; -SkipExtract reuses an extraction)
pwsh -NoProfile -ExecutionPolicy Bypass -File scripts/vehicle-kit/measure-wheels.ps1 -Spec scripts/vehicle-kit/specs/lightrp-rims.json
# Owner review board, into artifacts/vehicle-kit/lightrp_vk_rims/board
pwsh -NoProfile -ExecutionPolicy Bypass -File scripts/vehicle-kit/rim-board.ps1 -Spec scripts/vehicle-kit/specs/lightrp-rims.json
```

Run `measure-wheels.ps1` after `build-pack.ps1`: it then also reads each built part's
`centreBackX` and compares the depth of every rim centre with the stock one.

Last build: `VK_PACK_OK revision=f721d6538465 models=108 files=216 zip=5367672 previews=540`
(Blender 4.5.14 LTS, Cyberpunk IO Suite 1.8.0, WolvenKit cp77tools 8.20.0; not deployed).

This pack puts 216 files in one depot folder. `build-pack.ps1` used to deserialize each
folder in one WolvenKit call, and from a worktree's default `artifacts` path that command
line passed the Windows limit of 32 767 characters ("Nom de fichier ou extension trop
long"); the build above used a short `-OutDir` (`$env:TEMP\vk-e1e`). The script now
splits the call into batches, so the default path works. With a custom `-OutDir`, give the
same folder to `measure-wheels.ps1 -PartsDir <OutDir>\work\parts` and
`rim-board.ps1 -BuildDir <OutDir>`.

One LOD each (the pipeline default, like every custom mesh proven visible in game), all
under the 6k-triangle budget (the vanilla rim is 920, `README.md`). Every window-disc design
also carries a tyre valve.

Three material slots per rim: `rim_main` (face, spokes, hub, barrel), `rim_lip` (outer lip;
also the barrel on Wire 64, Steelie and Off-Road 8, like a one-piece steel rim) and
`rim_detail` (cap, lugs, bolts, rivets, ribs, valve, accents, the Turbofan backing disc).
The legacy styles of `parts.example.json` (`split`, `straight`, `turbine`, `mesh`) are
unchanged and keep their two slots.

### Window-disc faces

The ten newer styles build a cast or stamped face as one disc band pierced by windows (the
gaps between spokes, vent holes, hexes), not as separate spokes. The band is cut into
sectors along seams that run through solid material (spoke centre lines, radial lines
between holes); each sector holds one window, defined by a signed distance field in the
wheel plane (lines and circles joined with rounded intersections, so every corner is a true
fillet of a chosen radius; hexes are sharp). Each sector is a closed solid built from rays
cast out of its window: window edge with a chamfer (2.2 to 4 mm), front face on the style's
profile, back face, window wall and seam wall. Neighbouring sectors meet on their seams at
the same front surface, so no gap shows.

Rays are spaced by outline curvature and length (`max_turn`, `max_len`) plus one through
every boundary corner. That spacing is the triangle budget: the denser faces (Twin 6,
Y-Spoke 6, Vortex 7, Three-Piece 10) use the coarser `LEAN` spacing, and the Hex Mesh bands
are conical (linear profile) so their few large quads stay flat and shade without facets.

### Shared base geometry

Every catalogue rim is built in the wheel slot frame of the contract (E0.5): metres, spin
axis X, **outboard toward -X**, centred on the axle. All eighteen share one base so a single
fit per model serves the whole catalogue:

| | Value |
|---|---|
| lip radius | `0.28` |
| lip face | `x = -0.208` |
| width (face to back of barrel) | `0.30`, so the barrel ends at `x = 0.092` |

`make_rim.py` refuses to export (`VK_RIM_FAILED`) a rim with any vertex in front of the face
or beyond the lip radius, and records `measuredFaceX`, `measuredRadius` and `centreBackX`
(the deepest point within 0.4 R) in the part's `mount` metadata.

The exact slots of every pair are in the spec. Prop models are named `<part>_<finish>`, so
the variants are `asset:lightrp_vk_rims/rim_classic_chrome` and so on (108 models). The 24

**Limits.** The client registers at most 128 prop models per resource and 1 024 in all
(`PropModels.hpp`, `OwnerLimit` / `GlobalLimit`): this pack uses 108, so a further design
or finish set beyond 20 models needs a second rim resource. The server allows 32 variants
per part (`VehiclePartCatalogue.MaximumVariants`); here a part has 6.

Chrome is metalness 1, roughness 0.10, colour 0.66–0.69: the values of CDPR's own chrome on
`metal_base.remt`. Revision `71f872a21fa7` cooked every finish without a `Metalness`
texture, so the template's black default zeroed the metalness and chrome read as matte
grey in game; see "Finishes: metalness" in `../README.md`. Gloss black, satin black, gloss
white and candy red are dielectrics (metalness 0), which is how paints already rendered.

## How the mount table was measured

`measure-wheels.ps1` works from the offline dealer inventory
(`docs/generated/vehicle-components-dealer-2.50.json`) and the game archives, read-only,
into `%TEMP%\open77-vehicle-kit-wheels` (never into the repository):

1. **Plan.** For each of the 15 dealer models and the staff-only Rayfield Caliburn (added to
   the inventory with `dealer_components.py --extra caliburn`), the rim and tyre components of the player
   appearance (shadows skipped), plus any other mesh bound to a wheel, brake or axle slot.
2. **Extract.** Those meshes, the models' `.app` files, the entity templates and their
   deformation rigs, from `content` then `ep1`; meshes uncooked to glb (mesh only). The
   paths go to WolvenKit 40 per regex (one regex for the 932 player variants would pass the
   command-line limit), and only the `.app` files are serialized to JSON: the measurement
   reads the meshes from their glb.
3. **Measure** (`measure-wheels.cjs measure`). Every vertex of the finest LOD, after the
   component's own `localTransform` (position, rotation) and `visualScale` read from the
   `.app`, in its slot frame: face x (most outboard point), inner x, lip radius (largest
   radius within 3 cm of the face), outer radius, centre x span (r < 0.4 R), angular
   coverage, and for tyres the bead radius (smallest radius on the outboard half). Rim
   centres bound to a `brake_*` slot are moved into their wheel's frame through the rig.
   The slot frames themselves come from `vehicle_slots` (slot → bone + relative
   transform) over the rig's reference pose.
4. **Fit** (`measure-wheels.cjs fit`), per wheel:
   - **scale** `s = min(stock rim outer radius, tyre bead radius + 1.5 mm) / 0.28` on Y
     and Z, so the new lip tucks 1.5 mm under the bead (no hairline gap) and never grows
     past the stock rim. Cars: uniform. Motorcycles: X is the stock rim width / 0.30
     instead, because a bike wheel is seen from both sides and a uniform scale would push
     the barrel 9 cm out of the Apollo's tyre. The scale is computed for every wheel from
     its own tyre, so front and back are sized independently (see below).
   - **offset** `x = stock face x - scale.x * (-0.208)`: the new lip face is flush with the
     stock rim face. `y = z = 0`.
   - **hide**: the stock rim components of that wheel (never the tyre), plus rim centres on
     brake slots that reach into the new rim's volume.
   - a wheel whose offset differs by more than 2 mm, or scale by more than 1 %, from the
     reference wheel (front-left, or the bike's front) gets its own entry under `slots`.

### Front and back of different sizes

No second rim size is needed: the size is a property of the fit, not of the mesh. Each
wheel's scale comes from its own tyre bead, and a back wheel that differs from the front by
more than 1 % in scale (or 2 mm in offset) gets its own `slots` entry, which Light RP's
`tools/build_vehicle_kit.py` turns into a contract §5 `wheels` entry with its own `scale`.

| Model | Front scale | Back scale | Why |
|---|---|---|---|
| Galena | 0.856 | 0.818 | the back tyre has a smaller bead (0.228 against 0.238) |
| Semimaru | 0.994 | 1.050 | the back tyre has a larger bead (0.292 against 0.277) |
| Caliburn | 1.168 | 1.170 | same bead on both axles (0.326); the back is in `slots` for its offset: the stock back rim is the front mesh stretched to X 1.26, its face 8.3 cm deeper |
| Apollo | X 0.485, YZ 0.794 | X 0.675, YZ 0.754 | motorcycle: back tyre bead 0.210 against 0.221, wider back rim |
| Hella, Quartz, Thrax, Bandit | one scale | same | same tyre on both axles; only the offset (rim face depth) differs |

The Archer Hella's larger back rim (radius 0.2874, `../README.md`) is the `_01` mesh of its
other trims. On those trims the back tyre has the same bead as the front, so the fit, capped
by the bead, keeps one scale there too (Light RP's `vehicle_kit_trims.lua`: 0.9846 front and
back, back face 3.2 cm deeper). The rule "lip meets the tyre bead" keeps a front-sized rim
from looking small on a larger back wheel; the part of the stock rim beyond the bead is
under the tyre.

### Right-hand side

**No extra turn.** On all 14 cars the right slot frame is the left one turned 180° about Z
(the spin axis reverses, so -X still points outboard), and the stock right rims use the
left mesh with no rotation, or only a spin phase about X (Colby, Merrimac). A rim built for
the left side is therefore correct on the right as it is. Consequence for the directional
designs (Blade 12, Tri-Blade, Vortex 7, Turbofan): seen from outside, both sides show the
same sweep, so on one side it trails the rolling direction. A mirrored `_r` model would fix
that if wanted (it would cost a model per pair against the 128 limit).

"Deeper than stock" compares the deepest point of each rim's centre (hub, spoke roots,
within 0.4 R; `centreBackX` in the part metadata) with the stock rim's centre, both in the
slot frame, and is listed from 1 cm. No car in the dealer list has a separate brake
component on its wheel slots (discs and calipers, where modelled, are part of the stock
rim mesh and hidden with it), so the risk is clipping the suspension upright, not a disc.

### Excluded

- **Yaiba Kusanagi.** The rim and tyre are separate meshes, but the front rim is a hubless
  ring (stock rim radius 0.182 to 0.231 m) around a hub-centre steering assembly that fills
  the wheel centre: a spoked rim would run through it. The back rim alone could take one,
  but a mismatched front/back set is not offered. The reason is in the spec's
  `fitPolicy.exclude` and in the fit file's `excluded`.

No other model is excluded. Both motorcycles have the rim and tyre as separate meshes.

## Every other player vehicle (2026-11-07)

`specs/lightrp-rims-fit-player.json` extends the table above to every vanilla
`Vehicle.*_player*` record of game 2.50 (cars and motorcycles) that the table does not name.
It reuses the same 108 models (pack `f721d6538465` unchanged): a fit is numbers only.
Quest variants (`Vehicle.q<digits>_*`: `Vehicle.q000_hym_player_car`,
`Vehicle.q304_songbird_escape_player`) are out of the customization extension by the owner's
decision of 2026-11-07; the inventory leaves them out and `player-rim-fit.cjs` skips the
pattern too.

```powershell
# 1. Inventory: every player record, its wheel components per entity appearance, and the
#    measure plan (one model per distinct entity / .app / definition wheel variant)
python -I scripts/vehicle-kit/inventory/player_components.py --game $game --names $kark `
    --cache $scratch --scratch "$scratch\extract" --measure-plan "$scratch\player-dealer.json"
# 2. Measure every variant (same rules as above), into a raw fit keyed by variant
pwsh -File scripts/vehicle-kit/measure-wheels.ps1 -Dealer "$scratch\player-dealer.json" `
    -Spec scripts/vehicle-kit/specs/lightrp-rims.json -FitOut "$scratch\player-fit-raw.json" -OutDir "$scratch\wheels"
# 3. Per record: the fit, the exclusions, the per-appearance data, the base check
node scripts/vehicle-kit/player-rim-fit.cjs docs/generated/vehicle-components-player-2.50.json `
    "$scratch\player-dealer.json" "$scratch\player-fit-raw.json" scripts/vehicle-kit/specs/lightrp-rims-fit.json `
    scripts/vehicle-kit/specs/lightrp-rims.json scripts/vehicle-kit/specs/lightrp-rims-fit-player.json
```

Run of 2026-11-07: 86 records in 49 bodies (2 quest variants left out), 932 wheel variants
measured (833 fitted, 99 without a fit: burnt and damaged definitions, or a tyre that is not
its own component). 16 records belong to the table above: 59 others are fitted, 11 excluded.

**Rules, beyond the table above.**

- **Record fit** = the measured fit of the appearance a spawned car wears: TweakDB
  `appearanceName`, else the entity's default appearance.
- **Spawned appearance not fixed** (neither names one: the engine picks): the record's `hide`
  takes the stock rim names of every appearance (the client skips a name the car lacks), and
  each appearance whose main wheel moves more than 1 cm or scales more than 3 % gets an
  `appearances` entry (E1c rule, at most 32, most common variant first). Two records are in
  that case: the Mackinaw NCU (2 entries) and the Yaiba Muramasa (excluded, below).
- **Fixed appearance**: the plain fit. The other appearances are reachable only through a
  curated trim; their measured fits wait in `appearanceFits` (43 records, 675 entries) and
  every appearance is summarised in `appearanceSummary` (variant, delta, in or out of
  tolerance, other stock rim names).

## What the fit file adds to contract §5

The record-level `offset` / `scale` / `hide` is exactly the §5 shape. Four additions need
the lead's support, and degrade as described when a client ignores them:

| Key | Meaning | If ignored |
|---|---|---|
| `slots` | per-slot `offset` / `scale` (back axle differs on Galena, Apollo, Hella, Quartz, Thrax, Bandit, Semimaru, Caliburn) | the back rims get the front fit: wrong size or depth on those eight |
| `extraSlots` | Merrimac `wheel_back_left_b` / `wheel_back_right_b`: `offset`, `scale` and their own `hide` | the middle axle keeps its stock rims (not rimless, since their names are only in `extraSlots.hide`) |
| `slotNames` | motorcycles: contract slot → stock slot the stock rim binds to (`wheel_front_rot_set`, `axle_back_wheel` on the Apollo) | fine if the contract slot spins with the wheel; both frames have the same position and spin axis |
| non-uniform `scale` | motorcycles only, `[x, y, z]` | the props client already applies `scale` per axis as `visualScale` |
